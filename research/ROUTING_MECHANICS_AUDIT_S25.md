# S25 — Native routing-mechanics audit (read-only) and verdict on the road-redundancy throughput hypothesis

Sources: decompiled game code under `logs/appsrc/` (classes cited as `Class.method`, file:line). C = confirmed by code; I = inferred. Audit performed by a read-only explorer; load-bearing claims re-verified by me by direct inspection (`LaneModel.PathfindingCost` 107–127, `DispatchVehiclesProcess.Step` 100–102/139, `VehicleSpawningProcess` 26–31, `DestinationModel.AcceptVehicleArrival` 245, `ParkVehiclesProcess` 20/54, `GenerateDemandProcess` 432). Nothing was run; no episodes, no heuristics.

## 1. Route choice and cost (C)
* The search runs in native code (`ExternPathfinding` → `dpcPlatform`: `GetPathCost`, `GetPathNextEdge`, `AddEdge`, `ChangeEdgeCost`, `MergeNodes`; ExternPathfinding.cs 168–231). Managed code builds the lane list by repeated next-hop queries (`Pathfinder.CreatePath`, Pathfinder.cs 83–133); the multi-target variant first picks the nearest endpoint (70–81). Algorithm internals are not visible (I: incrementally maintained shortest-path tables per endpoint).
* **Edge cost = travel time:** `LaneModel.PathfindingCost = max(1, int(10·Length/SpeedLimit))`; carpark lanes ×2; Mothballed 100000; roundabout slowdown divided back out (LaneModel.cs 107–127). `SpeedLimit` folds in motorway speed, roundabout multiplier, right-angle/sharp-turn multipliers and an `intersectionSpeedMultiplier` for uncontrolled lanes with >1 outbound lane (`GameBehaviourModel.GetLaneSpeed` 486–551).
* Cost is set at lane creation and changed only on Mothballed transitions or drying roads (LaneModel.cs 157–170, 424, 552; `RoadChunkModel.UpdateLaneCosts` 925–934). The `CarparkPenalty/UTurnPenalty/…` constants in Pathfinder.cs 26–34 are unreferenced (dead). No traffic-light term in the cost.
* Both the outbound route (to a carpark entrance) and the return route are computed **once at dispatch** (DispatchVehiclesProcess.cs 113, 130–135).

## 2. Equal-cost alternatives (C)
Deterministic, no RNG, no splitting: house choice by strict `<` on min path cost (first in model order wins a tie; DispatchVehiclesProcess.cs 100–107), entrance choice by strict `<` (ExternPathfinding.cs 121–128), one next-hop answer per (node, endpoint) from the native table, so every car with the same origin lane and endpoint follows the identical lane sequence. No round-robin or least-loaded logic exists. The native tie rule inside `dpcPlatform` is the only unknown (I), and it is irrelevant to splitting because the answer is a single next hop.

## 3. Traffic density and routing (C)
Density never enters path cost or lane choice. `Vehicles.Count` / inbound lists are used only for lane release and hot-swap (LaneModel.cs 181–217), intersection admission (`RoadChunkModel.CanInboundVehicleEnter` 347–481) and traffic-light phase weighting (TrafficLightModel.cs 163–268).

## 4. Rerouting (C)
Triggers: a lane state change/addition (`LaneUpdateProcess` 296–305), Mothballed release (`ReleaseMothballedLanesProcess` 130–175), a next-hop mismatch after a graph change (`VehicleMovementProcess.MoveVehicleToNewLane` 488–495), and carpark events (`ParkVehiclesProcess` 57/80/102/180). Repaths are processed only if the lane graph changed since the last attempt (`VehiclePathfindingProcess.Step` 37–201; `latestLaneChangeFrame`), keeping the first two committed lanes. **No congestion, blocked-lane or timeout reroute**; the 45 s intersection-wait option only forces entry (RoadChunkModel.cs 445–449).

## 5. Capacity constraints on deliveries (C unless marked)
* Car-following: IDM-style acceleration (`VehicleMovementProcess` 576–603; time gap ≈ 1.0 s, min gap 0.1, vehicle length 0.65, lookahead 5). Single-lane capacity ≈ 1/(T + (s0+L)/v), below ~1 car/s (I).
* Intersections: chunks with ≤ 2 lanes always admit; otherwise red light, crossing/exit space (≈ 2 car lengths, `DoesVehicleHaveSpace` 576–620) and earlier-reserved vehicles block; priority by committed → distance → timestamp (282–345). Uncontrolled multi-road junctions also slow approach (251–259). Lights alternate on timers weighted by waiting cars; roundabouts give circulating cars priority.
* Destination approach: a car enters `ParkingAtDestination` one lane before the carpark (503–508); gets a random free space ((L−1)·3 spaces, `CarparkModel` 407–488) or, if none is free, **drives through and still scores** (`ParkVehiclesProcess` 106–114, 175–181). Service time 3 s (`VehicleParkingTime`), longest-parked evicted early when demand waits. No explicit queue; queues arise only from car-following on the single entrance lane per entrance (≤ 2 entrances, CarparkModel.cs 517–550).
* **Score is credited on arrival** (`DestinationModel.AcceptVehicleArrival` → `_scoreKeeper.AddScore()`, 242–248).
* Dispatch and demand: each house spawns exactly **2 cars once** (VehicleSpawningProcess.cs 26–42); every step, destinations with unassigned pins dispatch to the same-colour house with a waiting car and the lowest path cost (demand-driven, nearest by travel time; 26–109); a car must return to its driveway before it can be dispatched again (VehicleMovementProcess.cs 516–531). A pin appears every `20/(AverageCarsPerDay·multiplier·oscillation)` seconds per destination (GenerateDemandProcess.cs 423–433), capped per destination (overcrowding).

## 6. Would duplicating a 3–5-hop trunk segment raise throughput? (I, strongly supported)
No. Routes are static, density-blind and deterministic; an equal-cost duplicate carries no traffic from the same origins and adds branch points that trigger `intersectionSpeedMultiplier` (slower, costlier lanes) and admission conflicts at the convergence before the stub. A duplicate helps only if it is **strictly cheaper** in travel time for some origin (fewer turns/junctions, motorway) or reaches a second carpark entrance.

## 7. Empirical check against existing logs (no new runs)
If deliveries are demand-limited rather than throughput-limited, deliveries **per destination-decision** should be equal across policies even when per-house rates differ. From the S13 replicate logs (S8-C) and the S22 V0 logs (planner B), 12 seeds each: deliveries per destination-decision **0.0536 vs 0.0551**; per connected-house-decision 0.0436 vs 0.0313; connected houses per destination 1.14 vs 1.65. The S21 "30 % per-house throughput gap" is therefore **demand sharing**: the planners connect more houses to each destination, and each destination's pin arrival rate — not the road network — sets deliveries. At these loads the binding constraint is the per-destination demand rate (§5, GenerateDemandProcess), with the 2-car round-trip cycle and the entrance chain far from saturation (S23/S24 observed ≤ 2 visible vehicles per network at anchor 60 and 15–44 summed counts over 30 decisions at anchor 200).

## 8. Remaining critical uncertainty and the smallest probe
Whether the per-destination demand cap ever becomes non-binding in long native episodes (many houses per destination, overcrowding-driven demand growth) so that road throughput could matter late in a game. Smallest probe, if ever needed: in the existing S22/S24 raw logs (no new run), compute deliveries per destination-decision as a function of connected houses per destination; a plateau at ≈0.05 across 1–4 houses confirms the demand cap over the whole observed range. (A native run is not required for this.)

## Recommendation: **C — close the generic road-redundancy throughput hypothesis in this regime.**
Mechanism (C): routing is fixed at dispatch on static travel-time costs, never splits across equal-cost paths and never responds to density, so redundant road cannot redistribute traffic; deliveries at the observed loads are capped by demand generation per destination, which the logs confirm (equal per-destination rates across policies). Neither a bottleneck bypass (A) nor another routing bottleneck (B) has a mechanism to act on in this regime. What road topology *can* change natively is (i) which house is dispatched (nearest by travel time) and (ii) strictly cheaper routes via turns/junction counts — both affect latency, not the demand-capped delivery rate — and (iii) spawn placement (S22/S23). No RL, no architecture, no synthetic work proposed.
