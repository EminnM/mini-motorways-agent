This interface is itself the ideal read/write surface for external instrumentation later (Phase 4/7) — `GetModels<T>()` for state reads, `ScheduleCommand()` for actions — **if** a hook can obtain a live reference to the running `ISimulation` instance (not yet attempted; that's Phase 3/4).

**Simulation vs. rendering separation**: `Motorways.Models.*` classes (e.g. `ClockModel`, `HouseModel`) hold a `CurrentFrame`/`NextFrame` pair of `IFrame` structs (see `ClockModel.Frame` — CONFIRMED) — this is a fixed-timestep-with-interpolation pattern: the simulation advances in discrete frames using `Fix64` (deterministic fixed-point) time, while rendering interpolates between `CurrentFrame` and `NextFrame` using a `float alpha` for smooth visuals (`ClockModel.GetInterpolatedTime(float alpha)`). This means the true simulation state is delivered at whatever the simulation's frame rate is, separate from the render frame rate — important for Phase 5 (tick identification) and Phase 10 (acceleration): the simulation may not need to run in lockstep with `Update()`'s render calls.

**Dependency injection**: fields marked `[Dependency]` (e.g. `private CityModel _cityModel;`) are populated by a custom `Factory`/`Factory.Pools` scope system (`IScope`, `scope.Get<T>()`, `scope.Release(x)`), not Unity's `[SerializeField]`/component system. `IReusable` objects are pooled (`Reset()` method returns them to a clean state). This matters for Phase 3 hooking: naive `FindObjectOfType<T>` will not find these — they live in a custom `IScope` graph reachable from `AppContainer`/`MotorwaysAppContainer`, not the Unity scene hierarchy.

`ClockProcess.Step()` (CONFIRMED, full source):
```csharp
public void Step(ISimulation simulation, Fix64 deltaTime) {
    foreach (var clock in simulation.GetModels<ClockModel>()) {
        if (!clock.isPaused) {
            clock.NextFrame.time = clock.CurrentFrame.time + deltaTime * _city.Rules.GetClockSpeedMultiplier();
            if (!_city.Rules.CanExpansionTimeContinue || clock.expansionTimeManuallyPaused) deltaTime = Fix64.Zero;
            clock.NextFrame.expansionTime = clock.CurrentFrame.expansionTime + deltaTime * _city.Rules.GetClockSpeedMultiplier();
        }
    }
}
```
This is the actual game-speed multiplier application point — `_city.Rules.GetClockSpeedMultiplier()` (a `GameRules` virtual/property, not yet decompiled) is PROBABLE the 1x/2x/3x speed control's effect on the sim, confirming the clock scales with a rules-provided multiplier rather than the engine's `Time.timeScale`. Relevant to Phase 10 (acceleration): the simulation's notion of speed is entirely internal to `Fix64 deltaTime * multiplier`, not tied to wall-clock `Time.deltaTime` scaling, which is a good sign for being able to decouple simulation speed from rendering.

## 4. SPAWN PATH (CONFIRMED — full concrete answer)

Entry point: `BuildingSpawningProcess.Step(ISimulation, Fix64 deltaTime)` (`Motorways.Processes.BuildingSpawningProcess`, called every sim tick as one of the registered processes):

```
Step()
 ├─ ScheduleHouses(simulation)          — decide if/when a new house should be queued
 └─ SpawnScheduledBuildings(sim, dt)    — pop due entries off CityPlanModel.scheduledBuildings and place them
```

**4.1 Scheduling (deciding *that* something should spawn, and roughly *when*)**

Two code paths, selected per-city by `_city.Rules.UsesPerCityHouseGraph`:
- Default path (`ScheduleHouses`): for each active `DestinationModel`, if that destination group's house supply is insufficient (`!current.IsSupplySufficient`) and not already scheduled, call `ScheduleNewHouse(groupIndex, simulation)`.
- Curve-driven path (`ScheduleHousesFromCityHouseCurve`): compares live house counts per color-group against a target curve (`scheduleGroup.minimumNumSuburbs`/`maximumNumSuburbs`, evaluated against elapsed time) and schedules houses to catch up.

New destinations/houses are scheduled with `CityPlanModel.ScheduledBuilding` records that carry a `time` (when it becomes eligible to spawn), `groupIndex` (color group), `type` (`CityTileType.Supply` = house, `.Demand` = destination), and a `grouping` (`GroupingStyle`: `Near`/`Far`/`Normal`/`Circle`) that controls whether §4.2's weight system biases toward or away from existing same-group buildings.

**4.2 Placement — the actual "where can this go" answer (`BuildingPlacer`, CONFIRMED)**

`BuildingPlacer.StartPlacing()` builds a per-tile weight array over the current playable area. For each tile:

1. **Hard eligibility gate**, `IsTileBuildable()`:
   - `!_tilemapModel.IsTileReserved(tile)` AND `_city.Definition.TileIsZoneable(tile)` (or `ignoreUnzoneableTiles` override).
   - `tileModel.Tile.CanSetContentType(buildingType)` — the tile's current road/content state must allow the target content type.
   - **CONFIRMED "roads block spawning" mechanic, with an escape hatch**: if `_city.Rules.CanBuildingsDemolishUnusedRoads` is true for the current game mode, a tile that fails the plain content-type check can *still* become buildable if (a) none of its roads have permanence above `PercentageOfPermanenceTimerWhereRoadsCannotBeDemolished`, AND (b) a simulated "what if this tile were cleared" test tile (`CreateDemolishedTestTileFrom`) passes `CanSetContentType`, AND (c) the tile is **not** currently on a route connecting an active destination to an active house (`IsTileConnectedToBuildingAndHouse`, checked via lane-graph pathfinding `_lanePathfinder.AreLanesConnected`). This is a direct, code-level confirmation of the brief's Hypothesis #1 (occupying road space affects future building spawns) — **and** reveals the counter-mechanic: a road tile becomes spawn-proof once it forms part of an actually-used house↔destination route. This is per-game-mode (`GameRules.CanBuildingsDemolishUnusedRoads`), not universal — **UNKNOWN which specific game modes enable it** (GameRules subclasses not yet individually decompiled).

2. **Base weight**, `GetBaseWeightForTile()`: looked up from a `BuildingSpawningTileWeights` dictionary keyed by tile coordinate, itself built once from a hand-authored Unity `Tilemap` of `WeightTile`s per map (`CitySpawningLayerData`, loaded from `CityTileTypeDefinition`s — i.e. **level-design-authored spawn weighting**, not procedurally generated). A tile absent from the weighted-tile map gets `-1` (invalid) under `ExclusivelyUseWeightedTiles`, `0` under `AllowNonWeightedTiles`, or `1` under `IgnoreWeights` — `BuildingSpawningProcess` escalates through these evaluation levels as `spawnAttempts` on a scheduled building climbs past `_constants.MaxFailedBuildingSpawnsBeforeIgnoringWeights`, i.e. **the game relaxes its own placement rules over time if a building keeps failing to place** (CONFIRMED, `BuildingSpawningProcess.SpawnScheduledBuildings` weightEvaluationLevel logic).

3. **Dynamic weight scaling from existing buildings**, `ScaleTileWeightByBuildingInfluence()` — CONFIRMED, this is the direct evidence for Hypothesis #2 (building geometry/position affects future spawns):
   - Weight forced to 0 if the tile is adjacent to any demand tile (`distanceToNearestDemand <= 1`) or coincides with existing same/other-group supply.
   - Otherwise, exponential push/pull factors are applied based on Manhattan-ish tile distance to the nearest same-group demand/supply and cross-group supply, using tunable constants: `SpawnPushFactorVeryStrong=0.425`, `SpawnPushFactorStrong=0.6`, `SpawnPushFactorWeak=0.9`, `SpawnPullFactor=1.3`, decaying per-tile-of-distance (`Fix64.Pow(factor, distance)`), i.e. **buildings actively cluster ("Near"/pull) or spread out ("Far"/push) depending on the scheduled building's `GroupingStyle`**, purely from geometric distance to existing buildings — confirms that existing player-visible city layout materially reshapes where new buildings can appear next.
   - Separately, `StartPlacing()` also **zeroes out** (`-1`, hard-invalid) an area-of-effect around every roundabout center (all 8 neighbors, or just the 4 orthogonal ones if `AllowSpawnsOnRoundaboutDeadzone`) and around every active destination if `GameRules.UseDestinationDeadzonesFor(...)` is set for that content type (radius 5, `DestinationDeadzoneRadius`) — CONFIRMED deadzone mechanics tied directly to road/building geometry, not randomness.
   - `ChangeTileWeightsAroundBuilding()` additionally applies a soft exponential-decay blur (`blurFactor^distance`) around every existing house, scaled by the map's local `DensityGroup` (Low/Medium/High) which sets the falloff radius (`density * 2`) — i.e. **local pre-authored "density zones" on each map change how far a house's influence reaches**, another level-design lever on spawn behavior.

4. **Weighted-random final choice**: `TryGeneratePlacementForLayoutAtCoordinates()` sets `placement.weight = _cityModel.pseudorandomGenerator.Fix64(weight)` — i.e. a **uniform-random draw scaled by the tile's final computed weight**, not a deterministic argmax. `GeneratePlacements()` then sorts all valid placements descending by that drawn value and `ChoosePlacement()` walks the sorted list top-down, additionally requiring `PlacementDrivewaysAreFree()` (driveway tile must still be able to path away from the building without being permanently boxed in, unless `GameRules.AllowBlockingSpawns`) — confirmed **weighted-reservoir-style random selection among all valid candidate tiles**, using the deterministic simulation RNG (see §5), not `UnityEngine.Random` or `System.Random`.

**Answer to the brief's specific spawn questions:**
- *What constraints are checked before a building can spawn?* — zoneability, reservation, content-type compatibility (with a conditional road-demolition exception gated by route-usage and permanence), roundabout/destination deadzones, and driveway-pathability.
- *Do roads/road tiles participate?* — **Yes, directly and centrally** — see 4.2.1 and 4.2.4.
- *Is map occupancy/collision consulted?* — Yes: reservation flags, content-type state, and adjacency to other buildings all gate or scale weight.
- *Random, deterministic, or weighted?* — **Weighted-random**, using the deterministic per-city seeded RNG.
- *Where is the final decision made?* — `BuildingPlacer.ChoosePlacement()`, called from `BuildingSpawningProcess.SpawnScheduledBuildings()`.

## 5. RNG / DETERMINISM (CONFIRMED — two separate, unrelated RNG systems exist; do not conflate them)

This directly addresses the brief's explicit warning not to assume `FixedMath.dll` implies full determinism — the investigation found **two independent RNG systems** and they are **not both deterministic**:

1. **`Motorways.Models.CityModel.pseudorandomGenerator`**, type `PseudorandomGenerator` (top-level namespace, CONFIRMED full source, `types/PseudorandomGenerator.cs`):
   - A hand-rolled 64-bit integer PRNG: `_x *= _x; _w += _s; _x += _w; _x = rotl64(_x, 32);` (a Squares/xorshift-family generator), with a single fixed constant `_s = 13091206342165455529uL` and mutable `_x`/`_w` state set via `Seed`.
   - Outputs raw `int`/`ulong`, and a `Fix64()` method that constructs a fixed-point `[0,1)`-ish value directly from the raw bits via `FixMath.Fix64.FromRaw`.
   - **This is the RNG the simulation actually uses for gameplay-affecting decisions** — confirmed call sites: `BuildingPlacer.TryGeneratePlacementForLayoutAtCoordinates` (spawn tile choice), `BuildingSpawningProcess.AssessGroupingStyleForHouse`/`LevelUpDestinationBasedOnAge`/`ChooseRandomActiveGroupIndex`, `City.GenerateCityLayout` (initial city schedule randomization), `BuildingSpawningProcess` carpark-preference rolls.
   - Seeded via `Random.SetSimulationSeed(uint seed, IScope scope)` (CONFIRMED, top-level `Random` class) — **PROBABLE this is the per-city/per-map seed** that determines reproducibility (Phase 9 relevance), though where that seed itself originates (map hash? save file? fresh-random-per-game?) is **UNKNOWN**, not yet traced.
   - Being pure integer/fixed-point arithmetic with no floating point and no wall-clock dependency, this generator is CONFIRMED capable of bit-exact determinism given a fixed seed and fixed input sequence — consistent with `FixedMath.dll`'s presence, and with the game's own `FeatureToggle.ValidateSimulationDeterminism` + periodic `SnapshotCommand` scheduling seen in `MotorwaysGame.Tick()` (§6), which strongly suggests the *developers themselves* rely on and test simulation determinism internally.

2. **The static `Random` helper class** (top-level namespace, CONFIRMED full source, `types/Random.cs`):
   - Wraps a plain `System.Random _randomSource = new System.Random(Environment.TickCount)` — **seeded from wall-clock tick count, NOT reproducible across runs**, plus a `float`/`double`/`Vector2`/`Vector3` convenience surface (`Random.Float()`, `Random.Range()`, `Random.Shuffle()`, etc.).
   - This class also owns `_simulationSeedGenerator` (itself a `PseudorandomGenerator`) purely to *generate* new simulation seeds (`NextSimulationSeed()`) from the non-deterministic system RNG — i.e. **the seed for the deterministic generator is itself picked non-deterministically at some point**, unless externally overridden.
   - **Not yet traced**: which call sites in the ~1500 types use `Random.*` (the non-deterministic helper) vs `PseudorandomGenerator` directly. Given the naming and the spawn-path evidence above, HYPOTHESIS: `Random.*` is used for purely cosmetic/VFX/UI randomness (particle variation, audio pitch, etc.) while gameplay-state-affecting randomness consistently goes through a model's `pseudorandomGenerator` field — but this is **not fully verified** across the whole codebase and should not be assumed for any specific system not explicitly checked above.

**Practical implication for Phase 9 (determinism)**: reproducible training runs are plausible *if* (a) the simulation seed can be pinned externally (via `Random.SetSimulationSeed` or whatever calls it), and (b) all player-input timing is also made deterministic (the simulation's own frame-indexed command journal, see §6, suggests input timing already flows through a frame-indexed `Command` queue, which is exactly the mechanism needed for deterministic replay). This is PROBABLE, not CONFIRMED — untested end-to-end.

## 6B. LIVE COMPOSITION ROOT & SESSION LIFECYCLE (CONFIRMED LIVE — Phases 4/4B/5A/5B, post-instrumentation)

- **The live access chain, proven**: `UnityEngine.Object.FindObjectOfType<AppRuntime>().App.Game.Simulation` resolves to a real, stable `Server.Simulation` instance once a city session is active — `ReferenceEquals` held `True` across 12 samples spanning ~24 real seconds in a live test, and `Scope.Get<ClockModel>().Time` was observed climbing (0 → 1.1 → 1.8 → frozen while `IsPaused=True` → 2.7 → 6.7 → 10.7) tracking real gameplay exactly. ## 8C. ENVIRONMENT CORE: CONTROLLED STEPPING, TERMINAL STATE, AND THE PLAYER-ISOLATION INVARIANT (CONFIRMED — Phase 8, static + live)

- **`ISimulation.Step()` takes NO arguments** and always advances by exactly the fixed `Timestep` (`Fix64.One/10` = 0.1 simulated seconds), or by zero if paused — confirmed via decompiling `Server/Simulation.cs`. `MotorwaysGame.Tick(float)`/`Game.Tick(float)` is only an accumulator wrapper around repeated `Step()` calls using real/scaled frame time. Every registered `IProcess.Step` (including `LaneUpdateProcess`'s Pending→Active promotion) runs **inside** `Simulation.Step()` itself, so calling `Step()` directly, bypassing `Game.Tick` entirely, skips only `Game.Tick`'s own real-time/UI-driven side effects (view interpolation, audio, autosave-timer, upgrade-popup triggers) — never simulation correctness. This is the confirmed mechanism for controlled, frame-rate-independent simulation-time stepping. See `research/PHASE_8_ENVIRONMENT_CORE.md` §3.
- **`MotorwaysGame.HasGameEnded`** (public getter, private setter) is the sole authoritative native terminal flag, set exactly once by `OnGameEnd(GameEndReason)`. Under `GameMode.Normal` the only path to `GameEndReason.GameOver` runs through the UI screen stack (`DestinationModel.OnOvercrowded → GameplayEventHandler.EndGame → ScreenStack.PushScreen(GameOver) → GameOverScreen.TransitionIn → MotorwaysGame.OnGameEnd`) — a headless bootstrap that never drives the screen stack may never observe `HasGameEnded` flip to `true` even if a destination genuinely overcrowds. Confirmed live: all Phase 8 test episodes ended via truncation (decision/time limit), never via this flag.
- **A genuine, intentional stock invariant governs in-process player switching, confirmed via a live `ActivePlayer.PlayerChanged` event + stack-trace diagnostic**: `Motorways.Views.LoadingScreen.Tick()`, running on Unity's own per-frame `Update()` loop concurrently with any bootstrap (regardless of what the bootstrap does), has a permanent one-shot gate (`_hasActivatedPlayer`) that — the FIRST time it fires on a given boot — deletes every `PlayerDatabase.Players` entry with no chosen avatar and either `DateTime.MinValue` last-played time or zero recorded play time (exactly what a freshly `PlayerDatabase.CreatePlayer()`'d profile looks like), via `PlayerDatabase.DeletePlayer` → `RemovePlayer` → `ActivePlayer.ActivatePlayer(MostRecentPlayer)`. A disposable test player created and activated BEFORE this one-shot gate has fired will be deleted and the active player reverted, with NO code in `MotorwaysGame`'s DI construction graph involved at all (confirmed via an exhaustive, genuinely negative static trace of every `[Dependency]` field reachable from `Get<MotorwaysGame>()`). **The correct lifecycle ordering**: wait for `LoadingScreen`'s one-shot activation to fire naturally (confirmed via a strong signal — the `PlayerChanged` event's call stack containing `"LoadingScreen"`, not merely `HasActivePlayer==true`) before creating/activating any test player. Confirmed separately that switching players this way cannot alter `GameMode.Normal` simulation/road semantics: `MotorwaysGame.CreateRulesForMode` selects `GameRules` purely by the `GameMode` enum argument, with no player-identity branch anywhere in that path.
