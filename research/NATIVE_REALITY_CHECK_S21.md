# S21 — Native Reality Check and Research Direction

**Executive summary.** The project now has one component that demonstrably solves the synthetic task — the S18-H deterministic planner (≈160 median deliveries vs 8.5 for the learned S8-C policy) — and four learned-architecture experiments (S16 CNN/dilated CNN, S17 attention, S17-G GNN, S15 mixed PPO) that all failed to learn colour-aware routing from the current observation under small budgets. Nothing learned has been shown to beat a deterministic baseline in the native game. The native interface can run the planners today: a minimal raw-observation adapter was built and validated offline (48 real native states + 40,287 synthetic decisions through native-style JSON, 0 illegal actions). A paired 12-seed native protocol is specified below and awaits approval. The mechanics audit found one native dynamic that no baseline exploits and that learning could target — **spawn steering by road occupancy** (buildings cannot spawn on any road tile, and the placer's random-scaled argmax shifts with the candidate set) — plus confirmation that "pending removal" is observable only as `Mothballed`, that traffic is exposed only as a per-tile vehicle count, and that motorways/lights/roundabouts have no action interface. Recommended first question: **does deliberate road occupancy improve long-run spawn geometry and score beyond the planner, under an RNG-neutral control?** — a causal fork experiment, not RL.

## 2. Native integration readiness

**Interfaces (plugin `Entrypoint.cs`, Python `mini_motorways_env.py`):** IPC ops HELLO, PING, RESET(seed, max_decisions, decision_delta, start_mode), STEP(action[, overlay]), CLOSE, plus diagnostic ops DIAG_SNAPSHOT / DIAG_BRANCHES / DIAG_CF / DIAG_SPAWN / FREEPLAY (`Entrypoint.cs:4083–4094`). The Python env uses only RESET/STEP; there is **no Python-side save/restore/fork handle**. Snapshot/restore exists inside the DIAG ops (native save format + `SnapshotExtras` for PRNG, activation times, lane bookkeeping; restore-of-same-snapshot identical 15/15; two unexplained residual divergences recorded in `research/cf_probe/RESULTS.md`); whether the training DLL build includes them is unknown. Seeded reset is deterministic in principle but 3/12 identical-seed reruns diverged (S13a). Fixed decision interval = `decision_delta` (1.0 s in S9–S13).
**Action limits:** `ActionKind {Wait, Add, Remove, ChooseUpgrade}` (`:2469`); `ApplyAction` dispatches only TryAddRoad / TryClearTile / TrySelectUpgrade (`:2952–2968`). Missing: motorway, traffic-light and roundabout placement/removal, diagonal edges, single-edge REMOVE on multi-edge tiles, visibility of which upgrade each slot offers (only the pending count is exposed; the chosen type appears afterwards in `applyInfo`). Bridges/tunnels are implicit in ADD over water (consume the bridge budget; `TileEditor.cs:78–100, 241`).
**Observation limits:** per-tile `road{N,E,S,W}` state strings, content, `groupIndex` (integer, dropped by the v1 encoder), destination demand/overcrowding/`overcrowdingTime`, `visibleVehicleCount`; globals incl. resource totals. Not exported: per-vehicle data, per-lane queues, house waiting/owned vehicles, unassigned vs waiting demand (all exist in the unreachable `BuildSnapshotJson`, `:3466–3597`).

**Adapter (`research/s21_native_check/code/native_adapter.py`, 170 lines):** `NativeStateView` duck-types the S13-env attributes the S18-H `WorldModel` reads — content/groups per tile, houses with first-seen decision (visible history only), destination blocks = adjacent Destination tiles of the *same* `groupIndex` (adjacent blocks of different colours are separate native models — found by the equivalence test below), carparks by adjacency, demand/overcrowding from the tile's destination info, edges from the state strings (Active/VisiblyActive → functional, Mothballed → inactive, **Pending → present/non-functional/non-buildable**), stub/driveway edges, concrete from globals, and the native legal mask as the authority for legality. `NativePlannerPolicy.act(raw, mask)` wraps the frozen S18-H executor. No future or hidden information: the view is built from the PolicyObservation JSON only.

**Validation without the game (`adapter_tests.json`):** T1 on 48 saved native states (24 seeds × reset/first-house): content and groups equal to the S11 `Ctx` 48/48; functional and present edge sets equal to the S11 model 48/48; connectivity equal 48/48; planner's first action legal under the native legal set 24/24. T2 end-to-end: planners A and B driven through the adapter on native-style renderings of synthetic states vs run directly on the env, 36 scenarios each (spawns, driveway replacements, Mothballed edges, top-ups, mid-plan invalidations): **40,287 / 40,287 decisions identical, 0 illegal actions, 0 diverging episodes** (the first run found one divergence caused by merging two adjacent destination blocks of different colours; fixed by grouping on equal `groupIndex`, which is also how native models them). T3: a Pending edge is present, non-functional and not re-addable. Not validated offline (needs the game): behaviour on `Mothballed` roads awaiting release with vehicles, bridge-budget exhaustion, upgrade-choice interrupts (the planner emits WAIT when the mask only offers ChooseUpgrade — the S13 logs show 22 such decisions; the mask makes WAIT illegal then, so the executor's "illegal → WAIT" fallback would be masked: the runner must pick the first legal action in that case — flagged as an open item to fix before running).

## 4. Verified mechanics and unknowns (audit: `Entrypoint.cs`, decompiled sources under `logs/appsrc/` and `research/static_recon/`; CONFIRMED = code evidence)
**Building spawning (CONFIRMED).** Destinations come from the authored city plan with fixed colours and jittered times (`City.cs:358–418`); houses are scheduled for the destination group with insufficient supply (`BuildingSpawningProcess.cs:435–495`), so a new house's colour follows existing destinations. Placement: per-tile weights from the spawning layer scaled by distances to existing houses/destinations only — **no road terms** (`BuildingPlacer.cs:265–363, 741–816`); every feasible candidate draws one PRNG variate and the max of weight×variate with free driveways wins — a random-scaled argmax (`:580, 734, 818–835`). **Any tile with a road in any state (Pending/Active/Mothballed), motorway or roundabout is not buildable** (`Tile.cs:1094–1096, 1174–1199` via `IsTileBuildable`), except under Expert rules where unused roads may be demolished. Consequence: roads steer spawns by (i) removing candidates and (ii) shifting the PRNG stream for every later candidate and event — observed in 12/19 branches of the stopped spawn pilot (`research/spawn_counterfactual/PILOT_NOTES.md`). Size of the geometric effect: UNKNOWN (pilot stopped; its "far" control was not far and the RNG shift confounded it).
**Road deletion (CONFIRMED).** `RoadState` flags: None/Planned/Pending/Active/Mothballed (`RoadState.cs`). REMOVE sets the tile's roads to Mothballed immediately, no vehicle check (`ClearTileEdit.cs:41–59`); `ReleaseMothballedLanesProcess` sets them to None only when no vehicles are on or inbound to the lane, re-pathing inbound vehicles. So **Mothballed = pending removal**, and it is the same exported state as a displaced house driveway that can be re-activated — the two cases are **indistinguishable in the JSON**. Physical occupancy is only the per-tile `visibleVehicleCount` (traversing vehicles; inbound excluded). The v1 encoder maps Pending to 0.33 and the unseen `Planned` to 0.
**Traffic.** Natively: per-house waiting/owned vehicles, per-lane vehicle lists and inbound commitments, destination unassigned/waiting demand, overcrowding timer, per-vehicle state/position/speed. Exported to the policy: only `visibleVehicleCount` per tile (clipped at 10 by the encoder), destination `totalDemand`/`isOvercrowding`/`overcrowdingTime` (the last dropped by the encoder). No queue or route information. Not building a traffic model remains the right call.
**Infrastructure.** Native editors exist for motorways, traffic lights, roundabouts (`TileEditor.cs:447–592`); upgrades are granted by `UpgradeAwardingProcess` as weekly choices drawn with the behaviour PRNG (2 options; 9 in Expert), queued in `pendingUpgradeChoices`, selected by index. The plugin exposes `ChooseUpgrade(i)` but not what each slot contains; no placement actions for motorways/lights/roundabouts. **Unknowns:** motorway travel-time/capacity semantics (never inspected in play), bridge-budget replenishment rule, whether DIAG ops are in the training DLL.

## 5. Candidate research questions (≤3) and recommendation
**Q1 — Spawn steering by road occupancy (recommended).** *Hypothesis:* placing cheap, possibly disconnected roads on tiles where future houses/destinations would otherwise spawn changes spawn geometry in a way that raises long-run deliveries beyond a planner that only builds transport roads. *Mechanic:* roads block spawn candidates (CONFIRMED) and shift the placer's PRNG (CONFIRMED). *Baseline:* S18-H planner B. *Minimum experiment (no RL):* from anchored native snapshots (DIAG_CF/DIAG_SPAWN machinery, 15/15 restore fidelity), compare branches: planner-only vs planner + a fixed "occupancy" policy that spends k concrete on non-transport roads, against an **RNG-neutral control** that consumes the same number of PRNG draws without blocking tiles (e.g. a road placed where no spawn candidate exists, verified via the recoverable PRNG draw count noted in the pilot) — measure spawn positions, planner route lengths and score at 90–300 decisions. *Success:* consistent spawn displacement and a score gain over both controls larger than the restore noise on ≥ 8/12 seeds. *Confounders:* PRNG stream shift (controlled), concrete opportunity cost, Expert-rule demolition (not in Normal mode), the stopped pilot's reach problem. *Effort:* 2–3 days (probe DLL availability is the risk). *Meaning beyond the game:* intervening on an environment's generative process rather than its reward channel — a clean testbed for "shaping the future state distribution".
**Q2 — Removal timing under traffic (Mothballed release).** *Hypothesis:* a policy that schedules REMOVE/reroute when lanes are empty avoids the latency of deferred release and the re-pathing shock. *Mechanic:* deferred release (CONFIRMED). *Baseline:* planner B with immediate removal. *Minimum experiment:* snapshot branches comparing immediate vs delayed removal of a congested dead-end; measure release delay and deliveries. *Success criterion:* measurable release delay and a score effect above restore noise. *Confounders:* only per-tile vehicle counts are observable; indistinguishable Mothballed semantics. *Effort:* 1–2 days; value limited by observability.
**Q3 — Upgrade-choice policy.** *Hypothesis:* choosing among weekly upgrades (concrete vs bridge vs roundabout…) matters for survival. *Blocker:* the offered options are invisible to the agent; needs a plugin change to export them first. Not testable now.
**Recommendation: Q1 first**, as a causal fork experiment on native snapshots; RL only if the effect exists and the control-policy space is not trivially enumerable.
